# 嘭咔智能电子物料仓库管理系统开发提示词

你是一名资深全栈软件架构师、Web 前端工程师、后端工程师、数据库工程师、DevOps 工程师和软件测试工程师。

请从零开始为“嘭咔智能”设计、开发并交付一个完整、可部署、可运行的电子物料仓库管理 Web 系统。

该系统主要用于解决公司电子物料管理过程中存在的以下问题：

* 电子物料账面数量与实际数量不一致；
* 入库、出库、借用、归还、报废和盘点流程不规范；
* 无法快速知道某种物料是否有库存；
* 无法快速找到物料所在的仓库、柜子、抽屉和格子；
* 物料分类混乱；
* 无法追溯物料由谁领取、用于哪个项目；
* 无法判断项目物料是否已经被预留；
* 多名员工无法同时管理同一套库存数据；
* 低库存物料不能及时发现；
* 缺少完整的操作记录和责任追踪；
* 依赖共享表格时容易出现覆盖、冲突和数据版本不一致。

系统应当作为公司内部局域网 Web 服务运行。

员工只需要连接公司 Wi-Fi 或有线局域网，即可通过浏览器访问系统，不需要购买公网域名，也不需要安装客户端。

访问方式示例：

```text
http://192.168.1.50
```

也可以在公司局域网中配置便于记忆的内部访问名称，例如：

```text
http://material.local
```

系统必须在没有互联网连接的情况下继续正常运行。

# 一、项目基本信息

项目英文名：

```text
PengkaMaterialWeb
```

系统中文名：

```text
嘭咔智能电子物料仓库管理系统
```

主要用户：

* 硬件工程师；
* 仓库管理员；
* 采购人员；
* 研发项目负责人；
* 部门负责人；
* 系统管理员；
* 需要查询物料的普通员工。

核心目标：

1. 所有员工访问同一套库存数据。
2. 支持多人同时查询和操作。
3. 保证库存数据准确且不可随意篡改。
4. 所有库存变化都必须产生流水。
5. 所有重要操作都必须记录操作人。
6. 所有库存操作必须由服务端校验。
7. 防止超额出库、重复提交和负库存。
8. 支持项目物料预留。
9. 支持低库存提醒。
10. 支持盘点、借用、归还和报废。
11. 支持 CSV 和 Excel 导入导出。
12. 支持数据备份和恢复。
13. 支持公司局域网独立部署。
14. 不依赖任何外部在线服务。

# 三、禁止事项

不得采用以下做法：

* 不要只生成静态页面；
* 不要只实现前端界面；
* 不要只提供伪代码；
* 不要把正式库存数据保存在浏览器中；
* 不要使用 LocalStorage 作为库存数据库；
* 不要让前端直接连接数据库；
* 不要使用共享 Excel 文件作为正式数据库；
* 不要把数据库密码写死在代码中；
* 不要在代码中写死管理员密码；
* 不要允许前端直接修改最终库存数量；
* 不要允许通过物料编辑接口修改库存；
* 不要将全部后端逻辑写在单个文件中；
* 不要将全部前端逻辑写在单个页面中；
* 不要依赖公网域名；
* 不要依赖外部 CDN；
* 不要依赖互联网才能登录；
* 不要通过公网开放数据库端口；
* 不要为了快速完成而跳过事务和并发控制；
* 不要物理删除重要库存流水；
* 不要修改历史流水来掩盖错误；
* 不要在没有测试的情况下声称功能已经完成。

# 四、总体架构

采用浏览器、Web 服务和统一数据库架构：

```text
公司员工电脑、平板或手机
             │
             ▼
       Nginx 访问入口
             │
       ┌─────┴─────┐
       ▼           ▼
   Vue 3 前端   FastAPI 后端
                     │
                     ▼
              PostgreSQL 数据库
                     │
            ┌────────┴────────┐
            ▼                 ▼
        附件存储           自动备份
```

部署后，所有员工通过同一个局域网地址访问。

前端和后端优先采用同源部署：

```text
http://192.168.1.50/
http://192.168.1.50/api/v1/
```

默认不开放 PostgreSQL 端口给普通员工电脑。

# 十二、库存核心模型

库存字段至少包括：

```text
当前库存 quantity
预留库存 reserved_quantity
可用库存 available_quantity
```

计算关系：

```text
可用库存 = 当前库存 - 预留库存
```

必须始终满足：

```text
当前库存 >= 0
预留库存 >= 0
预留库存 <= 当前库存
可用库存 >= 0
```

所有库存变化必须通过统一的库存服务执行。

前端不得自行计算最终库存并直接提交。

# 十四、库存业务规则

## 1. 入库

* 数量必须大于 0；
* 增加当前库存；
* 不直接增加预留库存；
* 必须记录入库来源；
* 可以关联采购单；
* 可以关联供应商；
* 必须写入库存流水。

## 2. 出库

* 数量必须大于 0；
* 数量不得大于可用库存；
* 减少当前库存；
* 可以关联项目；
* 必须记录领取人；
* 必须写入库存流水。

## 3. 借用

* 借用数量不得大于可用库存；
* 必须记录借用人；
* 必须记录预计归还日期；
* 必须创建独立借用记录；
* 支持分批归还；
* 支持逾期状态；
* 不允许仅通过备注表示借用。

## 4. 归还

* 必须关联有效借用记录；
* 归还数量不得超过未归还数量；
* 支持部分归还；
* 增加当前库存；
* 更新借用记录；
* 写入库存流水。

## 5. 报废

* 报废数量不得超过当前库存；
* 报废后不能导致预留库存大于当前库存；
* 必须填写报废原因；
* 可以上传报废照片；
* 必须写入库存流水。

## 6. 退料

* 可以关联原始出库记录；
* 增加当前库存；
* 记录退料人；
* 记录退料原因；
* 写入库存流水。

## 7. 项目预留

* 预留数量不得超过可用库存；
* 不减少当前库存；
* 增加预留库存；
* 创建项目预留记录；
* 写入库存流水。

## 8. 取消预留

* 取消数量不得超过该项目现有预留数量；
* 减少预留库存；
* 更新项目预留记录；
* 写入库存流水。

## 9. 预留转出库

* 只能使用当前项目的预留；
* 同时减少当前库存和预留库存；
* 不允许占用其他项目的预留；
* 写入库存流水。

## 10. 盘点修正

* 输入实际盘点数量；
* 系统计算账实差异；
* 必须填写差异原因；
* 记录修正前数量；
* 记录修正后数量；
* 修正后不能小于已预留数量；
* 写入盘点记录；
* 写入库存流水。

## 11. 库位转移

* 不改变公司总库存；
* 记录转出位置；
* 记录转入位置；
* 记录转移数量；
* 使用数据库事务；
* 写入位置调拨流水。

## 12. 冲正

错误库存操作不得直接删除或修改。

需要通过一笔方向相反的冲正流水纠正。

冲正记录必须关联原始流水。

# 十五、多人并发与数据一致性

这是多人同时使用的系统，必须重点处理并发。

库存操作必须使用 PostgreSQL 行级锁或等效安全机制。

推荐在事务中使用：

```sql
SELECT quantity, reserved_quantity
FROM materials
WHERE id = :material_id
FOR UPDATE;
```

标准库存事务流程：

1. 开启数据库事务；
2. 锁定物料库存记录；
3. 读取当前库存；
4. 校验业务规则；
5. 更新库存；
6. 写入库存流水；
7. 写入业务记录；
8. 写入审计日志；
9. 提交事务；
10. 返回最新库存。

任何一步失败必须整体回滚。

禁止采用以下不安全流程：

```text
先查询库存
再离开事务进行判断
最后普通更新库存
```

必须验证以下并发场景：

```text
可用库存为 5
员工 A 同时出库 4
员工 B 同时出库 4
```

正确结果必须是：

* 只有一笔成功；
* 另一笔返回库存不足；
* 最终库存不为负数；
* 只有成功操作产生有效流水。

还必须测试：

* 两人同时预留；
* 一人预留、一人出库；
* 两人同时归还；
* 两人同时盘点；
* 重复点击提交；
* 网络超时后重试；
* 浏览器自动重发请求。

# 十六、幂等机制

所有库存写操作必须支持幂等。

每次库存操作携带：

```text
idempotency_key
```

要求：

* 同一个用户；
* 同一个业务接口；
* 同一个幂等键；

只能执行一次。

重复请求必须返回首次执行结果，不得再次修改库存。

前端要求：

* 提交后按钮立即禁用；
* 显示处理中状态；
* 每次业务提交生成唯一幂等键；
* 成功后刷新库存；
* 失败时显示明确原因；
* 不允许双击产生两笔操作。
